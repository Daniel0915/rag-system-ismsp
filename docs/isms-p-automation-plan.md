# ISMS-P 인증준비 자동화 챗봇 — 설계 계획

## Context

사용자는 논문 "RAG와 OCR 기술을 활용한 LLM 기반 정보보호 관리체계(ISMS) 인증관리 자동화 시스템" (진현준 외, 정보보호학회논문지 2025)을 분석해서, **영세한 기업들이 외부 컨설팅 비용을 줄이고 스스로 ISMS-P 인증심사를 준비할 수 있는 자동화 프로그램**을 만들고 싶어한다. 즉, 논문 저자들이 특정 한 기업을 대상으로 만든 프로토타입을, **여러 고객사(기업)를 대상으로 하는 제품**으로 확장하는 것이 목표다.

기존에 이 저장소에는 이미 TypeScript + Express + LangChain.js 기반 RAG 학습 프로젝트(00~07 모듈, Gemini/Ollama 프로바이더 스위치 포함)가 구축되어 있고, 이번 기능은 그 위에 새로 얹는 형태다.

## 논문의 핵심 기능 2가지

1. **근거 문서 탐색**: 기업이 업로드한 정책/지침 문서에서, 인증기준 항목(예: "2.10.5.1")별로 근거가 되는 조항을 자동 탐색. 2단계 검색 — ① 코사인 유사도 벡터 검색(1차, 유사도 %) → ② LLM이 인증기준과의 적합도를 재평가(2차, 문서 적합도 = α×유사도 + β×LLM판단, 논문값 α=1.0/β=0.3). 문서는 "장-조-항" 단위로 청킹하고 파일명 등 메타데이터를 함께 임베딩.
2. **증적 적정성 점검**: 스크린샷/사진/표 등 증적 자료를 OCR로 텍스트화(마크다운 변환) 후, 항목별로 미리 마련된 "판단기준"에 따라 LLM이 부합 여부를 판정. 논문은 PyMuPDF4LLM + Pororo OCR을 썼지만, 우리 코드베이스는 이미 Gemini 멀티모달로 이미지를 직접 분석하는 `loadImageAsDocument`(src/loaders/loadImage.ts)가 있어 별도 OCR 라이브러리 없이 대체 가능.

두 기능 모두 결과는 인증기준 항목별 GAP 분석 리포트(충족/부분충족/미충족, 근거 링크, 판정 사유)로 종합된다.

## 메타데이터/참고자료는 어디서 가져오나 (사용자의 두 번째 질문)

세 가지 층으로 구분된다:

1. **인증기준 마스터 목록** (공용, 전체 고객사 공통, 한 번만 구축) — 코드/공식 문항/카테고리/확인방식(문서만·증적만·둘다) 등 104개(전체) 또는 131개(간편인증) 행짜리 표.
   - 출처: KISA **ISMS-P 인증기준 안내서**(isms.kisa.or.kr, 무료 공개 PDF, 262p)와 **간편인증 세부 점검항목**(2024.7.24 시행 공지) — 둘 다 공식·무료 공개 자료.
   - 방법: 이 PDF들을 우리 시스템의 PDF 로더로 파싱해서 `data/isms-criteria.json` 같은 시드 데이터로 1회성 수동 큐레이션 (행 수가 적어 충분히 사람이 검수 가능).
2. **판단기준(증적 적정성 판정 기준)** (공용, 항목별로 미리 작성해야 함) — 가장 노동집약적인 부분. 논문 저자들도 294개를 직접 작성했음.
   - 합법적으로 쓸 수 있는 자료: ① 위 안내서의 항목별 상세설명(공식·무료), ② **공공데이터포털(data.go.kr)의 "ISMS_PIMS 연간 결함현황"** — 실제 심사에서 나온 결함 사례 데이터셋(무료·구조화됨, 논문의 [15]) → "심사원이 실제로 무엇을 확인하는지" 파악에 매우 유용.
   - 쓸 수 없는 자료: 논문이 참고한 시중 유료 교재("ISMS-P 인증심사 실무 가이드", 아크로북)는 저작권이 있어 텍스트를 그대로 긁어오면 안 됨. 사용자가 심사원 자격검정을 공부 중이라 그 책 내용을 알고 있을 수 있는데, 활용하려면 **책 문장을 그대로 옮기지 말고 본인이 이해한 내용을 패러프레이즈해서** 검수 UI에 입력하는 방식으로만 반영.
   - 제안: LLM이 (안내서 설명 + 관련 결함사례 몇 건)을 근거로 판단기준 초안을 자동 생성 → 사람이 검수/수정하는 반자동 파이프라인으로 294개를 처음부터 손으로 다 쓰는 부담을 줄인다.
3. **고객사별 문서** (테넌트별, 각 회사가 직접 업로드) — 정책/지침 문서, 증적 자료. 이건 우리가 어디서 "가져올" 게 아니라 각 고객사가 업로드하는 입력값 — 기존 04/05/06 모듈의 업로드+해시dedup+메타데이터 태깅 패턴을 그대로 재사용.

## 설계 자문(Plan agent) 결과 반영 — 중요한 인프라 이슈

기존 코드를 검토한 결과, 실제 운영 규모에서 문제가 될 수 있는 부분들이 있어 아래를 계획에 반영한다:

- **`VectorStore.rebuildIndex()`가 매 `open()`마다 전체 청크를 재임베딩한다** (src/vectorstore/store.ts) — 지금은 튜토리얼용 소규모 데모에선 문제없지만, 실제 기업 정책 문서 수십 개(수백 청크) 규모에서는 질문 하나 할 때마다 전체 코퍼스를 다시 임베딩하게 되어 비용·속도 모두 감당 불가. **본 기능 개발 전에 먼저 고쳐야 하는 인프라 이슈** — in-process 캐시(네임스페이스별 이미 만든 HNSWLib 인스턴스를 재사용, 실제 쓰기가 있을 때만 무효화) 또는 HNSWLib 자체 `save()`/`load()` + 신규 청크만 증분 임베딩으로 전환.
- **동시 쓰기 레이스 컨디션**: 청크 JSON 사이드카에 락 없이 read-modify-write — 동시 업로드 시 데이터 유실 가능. 네임스페이스별 쓰기 큐/락 필요.
- **기밀성 문제**: 보안 인증 준비 도구인데 고객사의 정책 문서·증적 스크린샷이 Gemini 클라우드로 전송됨 — 보안에 민감한 소기업 고객에게는 신뢰 이슈가 될 수 있음. 게다가 현재 `loadImageAsDocument`는 `LLM_PROVIDER=ollama`일 때 아예 에러를 던지므로, 정작 기밀성이 가장 중요한 증적 OCR 기능은 클라우드 LLM 없이는 동작 안 함. → 명시적 동의 안내 문구를 넣거나, 추후 로컬 비전 모델(qwen2.5vl 등) 지원을 검토.
- **테넌트 격리는 세션이 아니라 API 키/네임스페이스로**: `express-session`은 튜토리얼 채팅 이력용이지 테넌트 식별용이 아님. 회사별 API 키(env 화이트리스트 수준의 간단한 것부터 시작) → 서버 측에서 그 키로부터 네임스페이스를 도출(클라이언트가 companyId를 직접 보내지 않게 해서 경로 조작/타사 데이터 접근 방지).
- **장-조-항 청킹은 별도 함수로, 폴백 포함**: 소기업 정책 문서는 "제N조" 형식을 안 따르는 경우가 많으므로, 정규식으로 조항 밀도를 먼저 검사하고(예: `제\d+조` 매치가 3개 미만이면) 기존 `RecursiveCharacterTextSplitter`로 폴백. 각 청크에 `chunk_strategy` 메타데이터 태깅.
- **α/β 가중치는 논문의 고정값이 아니라 우리 데이터로 재보정할 하이퍼파라미터**로 취급.

## 단계별 계획 (Phasing)

**Phase 0 — 인프라 선행 수정 (이 기능과 무관하게 먼저 필요)**
- `VectorStore`에 네임스페이스별 인메모리 인덱스 캐시 추가, 실제 add/delete가 있을 때만 재구축(또는 신규 청크만 증분 임베딩)
- 네임스페이스별 파일 쓰기 락/큐 추가

**Phase 1 — 한 파일럿 기업 대상 얇은 수직 슬라이스 (5~10개 항목, 두 기능 모두 포함)**
- 인증기준 시드 데이터: 문서 확인/증적 확인 유형을 섞어 5~10개 항목만 우선 `data/isms-criteria.json`에 수동 큐레이션 (KISA 안내서 기준)
- 장-조-항 청킹 함수(폴백 포함) + 기존 `VectorStore`/`provider.ts` 재사용한 2단계 검색(유사도 → LLM 재평가)
- 해당 5~10개 항목의 판단기준은 이 단계에서는 **손으로 직접 작성** (자동 초안 파이프라인은 아직 안 만듦)
- 증적 점검: 기존 `loadImageAsDocument` 패턴을 확장해 "판단기준 목록을 받아 항목별로 판정"하는 새 함수로 일반화
- 최소한의 GAP 리포트 뷰 (항목별 상태 + 근거 링크)
- 목표: 전체 104~131개로 확장하기 전에 파이프라인 전체가 실제로 동작하고 정확도가 쓸만한지 검증 (논문처럼 실제 GAP 분석 결과와 비교)

**Phase 2 — 판단기준 반자동 작성 파이프라인 + 커버리지 확대**
- LLM 초안(안내서 설명 + data.go.kr 결함사례 근거) + 사람 검수 UI
- 증적만 확인하는 73개 항목 우선 확대, 이후 문서 확인 항목까지

**Phase 3 — 실사용 멀티테넌시**
- 회사별 API 키/온보딩, 동시성 안전한 저장, 기밀성 정책(동의 문구 또는 로컬 모델 옵션) 확정

## 재사용할 기존 코드

- `src/vectorstore/store.ts` — VectorStore (Phase 0 수정 대상)
- `src/vectorstore/ragChain.ts` — `answerFromDocs` (2단계 재평가 로직 추가 지점)
- `src/llm/provider.ts` — `createChatModel`/`createEmbeddings`/`generateStructured`
- `src/loaders/loadImage.ts` — Gemini 비전 기반 이미지 분석 패턴 (판단기준 기반 증적 점검으로 일반화)
- `src/modules/05-metadata-filtered-rag/step1_add_metadata.ts`, `step2_filtered_search.ts` — 청크 메타데이터 태깅 + 필터 검색 패턴
- `src/modules/04-multi-pdf-rag/step1_multi_load.ts` — 해시 기반 신규/변경/스킵 업서트 패턴
- `src/routes/uploadMiddleware.ts` — 업로드 미들웨어

## 검증 방법

- Phase 1 완료 시: 실제(또는 마스킹된) 정책 문서 + 증적 자료 소량으로 5~10개 항목에 대해 근거 문서 탐색 결과와 증적 판정 결과를 사람이 직접 검토해서 정확도 확인 (논문처럼 실제 GAP 분석 보고서와 대조)
- Phase 0 수정 후: 청크 수백 개 규모 네임스페이스에서 질문 1회 응답 시간이 재임베딩 없이 눈에 띄게 빨라졌는지 확인
